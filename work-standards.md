# Work standards

ANISH works directly in the code: create, debug, and iterate there.

- Answer in concise, complete sentences. State the point directly.
- Use affirmative wording. Skip contrastive asides such as "X, not Y" when nobody asked about Y.
- Change a web app's UI, layout, routing, client state, or rendered data only if you then verify the affected flow in the browser: use it the way a person would, check routes that share the changed state, and check the edge states the change touches. For layout changes, check a desktop width and a phone width.
- Commit only when asked. Push only when asked. Leave git config alone.
- Keep this vault as the shared source of truth. Put project-specific notes in that project. Do not copy this vault into each repo.
